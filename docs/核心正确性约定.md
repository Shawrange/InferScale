# InferScale 秋招版：四项核心正确性约定

更新：2026-09-22。状态：**P0–P2 及 P3 四策略 CPU 部分已实现，139 项测试通过；真实 GPU 契约和实验汇总继续推进**。

适用范围：一个 Gateway 进程、一个模型、两个同构独立 Replica、单信任域、文本生成、`n=1`。Worker 的推理请求全部经过 Gateway。本文是当前实现和测试依据；不要求构建完整生产平台。

## 1. 成本公式：比较 Worker 已承担的工作

### 1.1 必须去掉的误解

原公式 `score_i = queue_i + request_cost + kv_i` 中，同一个请求的 cost 对所有 Worker 相同，不会改变排序。新公式的有效信息必须来自 **Worker 上尚未完成的请求成本**。

```text
output_estimate_r = min(output_cap_r, predicted_output[model, prompt_length_bucket])
cost_r = p * prompt_tokens_r + d * output_estimate_r
C_i = sum(reservation.cost for unfinished attempts on Worker i)
n_i = number of unfinished local attempts on Worker i

q_i = n_i / request_capacity_i
score_cost(i, r) = wq * q_i + wc * (C_i + cost_r) / cost_reference
```

首版不把 KV、GPU 利用率、队列 EWMA 全塞入公式。远端 health、陈旧指标和容量阈值用于候选过滤；KV 可观测但不参与成本主实验，减少归因混淆。`cost_reference > 0` 是同模型池固定的配置尺度，各 Worker 相同，整轮实验不改变。

`p,d` 为非负权重，至少一个为正；Cost-Aware 的 `wc > 0`，`wq >= 0`。首轮可以用 `p=d=1`，只表示加权 token 工作量，不能宣称单位是 GPU 毫秒。预测缺少历史时用配置默认值；bucket 只取到达时已知的 prompt 长度，不使用实际输出长度或基准 workload 名称。

同构 Worker 下，新增的 `cost_r` 仍是共同项，**不会直接改变本次排序**；选定后立即把它加入对应 Worker 的 C，影响后续选择。这样称为“已分配未完成工作量感知”才准确。首版 C 在请求结束前不递减，可能高估将结束的长请求，不声称精确预测剩余时间。

### 1.2 可手算的例子

令两个 Worker 都有 2 个请求，容量为 4；`wq=wc=1`，`cost_reference=10000`，新请求成本为 1000。

| Worker | 当前请求数 | 未完成成本 C | Least Load q | Cost-Aware score |
|---|---:|---:|---:|---:|
| A | 2 | 9000 | 0.5 | 1.5 |
| B | 2 | 1000 | 0.5 | 0.7 |

Least Load 平分，Cost-Aware 选择 B。预占后 B 为 3 个请求、C=2000；释放此 attempt 后精确恢复为 2 个请求、C=1000。

### 1.3 更新规则

- 选择 Worker 和写入成本 reservation 在同一个短临界区完成，中间不 await。
- 每个 reservation 保存分配时的成本；后来 EWMA 改变也不能改变其释放金额。
- 仅正常完成且有可信 usage 的请求更新预测：`new = alpha*observed + (1-alpha)*old`，`0 < alpha <= 1`。
- 失败、取消或缺失 usage 不更新预测；触及输出上限的样本保留 length-capped 标记，报告偏差，不当作无偏自然长度。
- tokenizer 使用与后端一致的模型 revision 和 chat template。成本统计输入 token，不按字符数估算；单测可用固定 token fixture。
- 同分采用轮转；数据缺失、冷启动遗留负载无法解释时回退 RR，并记录原因。每轮正式实验重新建立干净状态。

### 1.4 必须通过的用例

| ID | 输入/动作 | 预期 |
|---|---|---|
| C1 | 上表的两个 Worker | 选择 B，分数等于手算值 |
| C2 | 相同快照，只改变当前请求成本 | 同构池排序不变；被选中 Worker 的预占量随成本改变 |
| C3 | 先分配一个大请求，再来后续请求 | 后续决策看到已预占成本，无需等采样更新 |
| C4 | reservation 后改变 EWMA，再完成请求 | 释放原 reservation 成本，账本无残差 |
| C5 | 失败/取消/无 usage，或未知模型特征 | 不污染预测；无虚构 token 数据 |

## 2. 请求计数：唯一账本和统一回收

### 2.1 两种身份和一个事实来源

```text
request_id：一次用户请求，跨重试不变
attempt_id：一次上游执行；至多 2 个，顺序执行

active_requests: dict[request_id, RequestLease]
reservations: dict[attempt_id, Reservation(request_id, worker_id, epoch, cost)]
```

global 活跃数取 `len(active_requests)`；Worker 活跃数与成本从 reservations 派生。首版两个 Worker 直接求和即可，不维护多份容易漂移的 mutable counter；后续性能需要才加索引和一致性校验。远端 sampled running/waiting 单独保存，不能再次加到本地请求计数上。

单进程共享状态由一把短锁保护。准入必须是“检查容量+插入 request lease”；调度必须是“过滤+打分+插入 reservation”。锁内没有 HTTP、tokenize、日志写盘或其它长操作。Gateway 等待队列为 0，满额立即 503。

### 2.2 资源所有权

请求控制器从入口到终态拥有 request lease；attempt 上下文拥有上游 response 和 reservation。统一 finalizer 根据 request ID 找到所有尚存 attempt，不只依赖调用方某个局部变量，因此“预占后、拿到返回值前取消”也可回收。

```text
request try/finally
  acquire request lease
  attempt 1 try/finally
    select + reserve
    connect / prefetch / relay
    bounded close upstream
    release attempt 1 reservation
  if eligible: attempt 2 uses the same request lease
finally
  bounded close any remaining upstream
  release all owned reservations
  release request lease
  record logical outcome once
```

释放采用受锁保护的 `pop(id, None)`；存在才释放，不存在直接返回。对同一对象两次 release 不减两次。成本由剩余 reservation 求和，自然避免“重试 B 却误减 A”或浮点反复减法残留。注册所有权和插入 reservation 同时完成。

异步 close 设 cleanup deadline；即使 close 异常/超时，本地 lease/reservation 也在 finally 中清除。取消后允许有界清理，不吞掉取消异常。关闭结果不确定时将旧 Worker 标为 SUSPECT，不继续投新请求；以探测及远端负载归零或明确实例重启恢复，不能只因等待几秒就断言已取消。这样既不泄漏网关计数，也不假装后端工作已经消失。

GPU 上还需验证断开确实停止该请求。缓存可能保留，不要求显存清零。远端指标不可得时保持不可调度并记录原因；这种保守故障行为可以接受。

### 2.3 必须通过的用例

| ID | 故障位置 | 预期 |
|---|---|---|
| L1 | 正常完成、参数错误、无 Worker | 静止后 active/reservations 为空 |
| L2 | reserve 后、连接中、首输出等待、转发中分别取消 | 每种路径回收完整；结果只记一次 |
| L3 | A 失败后切 B | request 活跃数始终为 1；A reservation 先释放，B 独立预占 |
| L4 | 完成与取消竞争，finalize 调用两次 | 不出现负数，不释放其他请求 |
| L5 | upstream close 抛异常/超时 | 本地计数收敛；旧 Worker 暂停接流量 |
| L6 | 并发数超过 global/per-worker 上限 | 原子拒绝，不超额；同一次采样内能看到新预占 |

失败验收不能只看最终 HTTP 状态码；同时断言账本、连接句柄和后台任务均已清理。

## 3. 流式重试：响应提交后绝不切换生成流

### 3.1 提交边界

首 token 与首 SSE 事件不同。role-only、空 delta、usage 和 heartbeat 都不算首个文本输出。

首版在发出 HTTP response start 前，读取并有界保存上游前导事件，直到首个非空文本输出或合法结束。提交后原序转发缓存和后续事件。首输出计时始于第一次 upstream forward，跨 retry 不重置；overall deadline 从入站开始，覆盖所有 attempt。

维护 `commit_started`、`response_started`、`body_bytes_sent`、`first_output_at`。在调用 ASGI response start 的 send **之前**设置 `commit_started=True`，即使 send 抛错导致是否送达不明，也不能重试。`response_started` 记录 send 成功，不能作为唯一重试条件。

**不要在已经返回的 StreamingResponse 生成器内部才决定是否重试。** 预取/重试必须在响应提交前的控制器完成，或由明确控制 ASGI send 的响应对象完成。断开监测覆盖预取期间；只有一个明确的 receive 消费者，避免与读取请求体/框架断开监听竞争。

### 3.2 唯一重试条件

```text
retry = attempt_number == 1
        and not commit_started
        and not client_disconnected
        and remaining_deadline > 0
        and failure in {connect_error, connection_reset, precommit_truncated_stream, upstream_502_503_504}
        and another_schedulable_worker_exists
```

最多跨 Worker 重试一次，排除已失败 Worker。httpx/transport 自动重试关闭。业务 4xx/429、无剩余预算、首输出/整体超时默认不重试；实现时明确区分客户端错误和 Worker 故障，不能一律摘除。

旧 attempt 的所有前导事件丢弃，旧 response 清理，旧 reservation 释放，然后新建 attempt。第二次执行必须沿用 request lease、总 deadline 和原始请求参数。响应最终只能来自一个 attempt。

### 3.3 提交后失败

保持已经发送的数据，关闭流，记录 `partial_response_failure`；不切 Worker、不重放，不追加成功 `[DONE]`。秋招版先采用“连接中止+客户端识别缺少合法终止”，不增加自定义 SSE error 协议。benchmark 只有看到合法终止序列才记成功；普通 EOF 不自动成功。

合法无文本完成可成功，TTFT 为 null。非流式响应在完整、有大小上限的 JSON 可用后才提交；本地没有首 token 可观察时不报告非流式 TTFT。

前导总字节、单事件字节、首输出等待都有上限，达到上限直接失败；转发采用按需读取并设下游写 deadline。SSE parser 支持跨网络 chunk、多事件同包和 UTF-8 分片；网络包不等于 SSE 事件。

### 3.4 必须通过的用例

| ID | 场景 | 客户端可见结果 |
|---|---|---|
| S1 | A 返回 role-only 后断开，B 成功 | 只看到 B 的完整响应，A 的 ID/role 不泄漏 |
| S2 | A 已输出文本后断开 | 收到 A 的部分输出后失败；B 调用次数为 0 |
| S3 | response start 已尝试但 send 抛错 | 禁止重试，即使记录的 bytes_sent=0 |
| S4 | 两个 Worker 都在提交前失败 | 一个明确 HTTP 错误；不返回空的成功 SSE |
| S5 | 预取时客户端断开 | 关闭 A，不尝试 B，账本回收 |
| S6 | role-only/usage/空输出/缺 DONE/跨包 SSE | 首输出计时和成功判定符合上述规则 |

用本地真实 socket 做重试、断开及慢读验证；S3 用 ASGI send 故障注入确定性覆盖“提交结果不明”，S6 的逐字节/换行边界另用 parser 单测补齐。内存 transport 不能独自证明网络提交和断开行为。

## 4. 实验口径：原始样本可复算

### 4.1 只保留三类主实验

| 数据集 | 比较 | 要回答的问题 |
|---|---|---|
| Mixed：长短 prompt/output 混合 | RR、Least Load、Cost-Aware | 相同请求数但成本不同时，成本账本是否改善 TTFT 尾延迟？ |
| Shared Prefix：长公共前缀+不同后缀 | Cost-Aware、Prefix-Aware | affinity 是否减少首输出等待，实际缓存命中是否变化？ |
| Hot Prefix：热门前缀+预设不均衡负载 | Cost-Aware、Prefix-Aware | 亲和是否导致热点，容量门槛能否分流？ |

四种策略可在所有数据集运行，但不必增加六种 workload 和完整权重 sweep。Prefix 权重只取事先选定的少量值，测试集不调参。算法改善必须靠 GPU 实验，fake Worker 只验证语义。

### 4.2 必须保存的数据

`manifest.json` 保存代码/依赖/后端版本、GPU、模型/tokenizer/template、引擎参数、四种策略参数、seed、负载文件摘要、采样默认值、cache 状态、warmup 与测量时长。

`requests.jsonl` 每个计划请求一行：request ID、计划到达、实际发送、首/末有效输出、终态时间、outcome、error subtype、usage token 数或 null、attempt 数、最终 Worker。未发送的计划请求也要记录。`attempts.jsonl` 单独记重试与成本分数，不把 attempt 当新请求。

`summary.json` 和 `report.md` 从以上记录生成；时间用同一客户端 monotonic clock，不能把客户端和服务器时间直接相减。Gateway 日志用于关联 Worker/attempt，不能伪装精确后端 queue/prefill。

### 4.3 指标定义

| 指标 | 定义与边界 |
|---|---|
| TTFT | client_first_content - client_sent；role/usage 不计入；无文本/非流式为 null |
| E2E | client_terminal - client_sent；成功延迟分布与失败耗时分列 |
| Chunk interval | 两个非空 SSE 内容事件的到达差，不称逐 token ITL |
| TPOT estimate | `(last_content-first_content)/(output_tokens-1)`，只对成功且有可信 usage、token 数>1 的请求计算；多 token chunk 会影响精度，标注估计值 |
| Request throughput | 测量窗口内成功终结的逻辑请求数/窗口秒数；attempt 数另列 |
| Output throughput | 测量窗口内成功终结请求的 usage output token 总数/窗口秒数；明确是按完成请求归属，不是逐 token 窗口精确计数 |
| Reject/error rate | 已发送请求为分母；另报占计划请求比例，不能隐藏客户端未发送 |
| SLO goodput | 测量窗口内成功且满足预先固定 TTFT/E2E 阈值的请求数/秒 |
| Cache hit | 真实后端对应 counter 的窗口增量之比，记录 token/block 等单位；不同于 affinity 命中率 |

成功请求的 P50/P95 必须同时给出成功数、拒绝数、错误数。P99 仅在样本量足够时附加，不能用几十个请求包装尾延迟结论。output tokens 不可用时为 null，不能用 SSE chunk 数、max_tokens 或重分词估计冒充真实 usage。

### 4.4 到达过程和分母

先实现 closed-loop 固定并发作冒烟，再用 open-loop 固定计划轨迹作主要策略比较。open-loop 的下一次到达不等待前一次完成；到达时发送器槽位已满则记 `not_sent: client_capacity`，不能等待槽位并仍称原到达率。

每轮按实际发送延迟容差检查发送器是否跟得上；超出预设阈值或发生本地丢弃的轮次标记“负载生成受限”，不能用作正式收益结论。记录 scheduled-to-sent lag，不能悄悄移动计划时间。

测量阶段停止后做有截止时间的 drain；剩余请求取消并记录。将窗口内完成吞吐和本轮请求 cohort（含窗口后结束）的完成/失败分布分别输出，不能把 drain 中完成数除以原窗口时长充当吞吐。

最终 cohort 必须满足：

```text
planned = not_sent + sent
sent = succeeded + rejected + failed + cancelled
attempts >= sent_to_upstream_requests
```

四种 sent outcome 互斥；timeout 是 failed 的子类型，不重复求和。客户端主动断开为 cancelled；Worker 中途失败为 failed。重试两次最终成功仍只计一个 succeeded，失败 attempt 单列。

### 4.5 公平比较

- 固定同一个模型、两个同构副本、全部引擎/采样参数、请求数据和 arrival trace，策略之外参数不变。
- 使用相同 tokenizer/template 验证 prompt 长度；实际 output 分布照实报告。强制生成长度的合成实验必须标注，不能当自然请求。
- 编译/模型预热与 prefix cache 预热分开。正式轮次统一重置或构建指定缓存状态，并同时重置 affinity、EWMA 和账本。冷/热结果分别报告。
- 每个配置至少重复 3 轮，随机化策略顺序；报告每轮结果及均值/范围，样本不足时不强调 P99。
- 单独做 direct 单 Worker 与 Gateway 单 Worker 对照估计代理开销；多副本策略比较保持 GPU 总数相同。
- 所有策略共用准入、超时、重试和容量门槛。可以报告没有收益或有退化，不强行得出 Prefix/Cost 一定更好。

### 4.6 必须通过的用例

| ID | 人工样本/场景 | 预期 |
|---|---|---|
| B1 | sent=0、role=10ms、content=40ms、last=100ms、end=120ms、tokens=4 | TTFT=40ms，E2E=120ms，TPOT estimate=20ms |
| B2 | 10 planned：2 not_sent、5 success、1 reject、1 timeout、1 cancel | 各恒等式成立；timeout 不被重复计数 |
| B3 | 一个逻辑请求尝试两次后成功 | success=1，attempts=2 |
| B4 | 窗口后 drain 完成一个请求 | cohort 成功数包含它，窗口吞吐不包含它 |
| B5 | chunk 数不等于 usage token 数或 usage 缺失 | 不按 chunk 推造 tokens/TPOT |
| B6 | open-loop 服务变慢 | 计划时间不漂移；发送器过载显式标记 |

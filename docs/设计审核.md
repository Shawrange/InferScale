## 1. 结论

**架构方向可行，可以启动基础工程；在进入策略对比和 GPU 验收前，需要先落实下列关键契约。**

值得保留的设计：Replica 与 Engine 两级调度边界；单进程 Gateway/Scheduler；本地 soft state；热路径不访问 Prometheus；四类策略共用输入输出；基于真实实验陈述收益；v1 不做 KV 迁移和分布式强一致调度。

主要风险集中在请求账本、流式协议和实验口径，不能靠后续调权重解决。尤其不应按原 Phase 4/5 先做高级策略，再到 Phase 6 补取消、超时和容量控制。

优先级定义：P0 为相关模块编码前必须定下的正确性或隔离契约；P1 为功能/GPU 验收前必须补全；P2 为实验可解释性和交付质量改进。

## 2. 发现清单

### R01 · P0 · Cost-Aware 的主公式不能产生所声称的成本感知排序

位置：原 §15.3，行 676–703。

同一个请求的 `normalized_request_cost` 若对所有同构 Worker 相同，则是公共常数：`argmin(q_i + c_request + k_i) = argmin(q_i + k_i)`。§15.4 虽提到 inflight cost，但仍是建议，也没有对应账本和释放规则。按主公式直接实现，可能得到名义上 Cost-Aware、实际上只看队列和 KV 的策略。

修正：必须维护每个 Worker 的未完成 attempt 成本和容量基准，使用 `(reserved_cost_i + incoming_cost) / cost_capacity_i`。同构 Worker 下 incoming 项仍不改变当次排序，收益来自已分配请求的成本差异；应诚实说明其是“未完成工作量启发式”，不是精确服务时间预测。单测设置相同请求数、不同历史请求长度，验证选择结果不同于 Least Load。

### R02 · P0 · 周期采样之间缺少原子预占，会产生瞬时流量集中

位置：原 §9–12、§14、§25；尤其 §25 的 1 秒采样。

大量并发请求可能看到完全相同的 Registry 快照，并全部选择同一 Worker。仅有后台采集，无法反映刚做出的路由决策。失败、重试、取消时没有 attempt 级账本，还会让计数重复释放或永久泄漏。

修正：增加 `AdmissionLease`、`AttemptReservation` 和统一 RequestFinalizer。`过滤 → 选择 → 预占` 在同一个短临界区完成，网络和 tokenizer 调用在锁外。采样状态与本地账本分别存储，不能把同一批请求重复相加。首版要求 Worker 仅由该 Gateway 写流量，局部请求数和成本以账本为准，远端队列/KV 为辅助信号；启动重建期间对远端已有工作量作保守降级。

验收：两个空 Worker、同一采样周期内突发请求也能分散；所有异常注入后租户/global lease 归零；每个 attempt 的 reservation 恰好释放一次。

### R03 · P0 · 重试边界与 HTTP/SSE 提交边界未统一

位置：原 §8、§20–23，行 316–373、921–1051。

首个 SSE 事件可能只有 role、空 delta 或 usage。若 Gateway 已发出 HTTP 200 或部分 SSE 元数据，即使尚无文本 token，也不能再随意更改状态码或透明拼接另一条生成流。原状态机也未覆盖非流式成功、合法无文本结束和多次 attempt。

修正：分别记录 `response_started`、`body_bytes_sent`、`first_output_at`。建议首个有效输出或合法终止事件之前延迟提交响应，缓存仅限有界前导事件；提交后不自动重试。预提交失败才可在总 deadline 内跨 Worker 重试一次。将“重试前首 token”改成更明确的“客户端响应提交前可重试”。

增加 HTTP 错误映射、SSE 截断规则与非流式分支。流中错误可以按约定输出 SSE error 后关闭，但这是需文档化的兼容扩展，不保证所有 SDK 都识别；不能发送成功 `[DONE]` 掩盖失败。

### R04 · P0 · affinity 盐值无法单独隔离真实 KV Cache

位置：原 §29，行 1211 起。

原方案只给 Gateway 的 prefix fingerprint 加 tenant salt。同一后端仍可能复用其自身缓存，所以这只能隔离 affinity 表，不能据此声称后端缓存跨租户隔离。

修正：默认信任域由鉴权结果产生，同时用于 affinity key 和后端 cache salt；客户端不能覆盖。所选 vLLM 版本必须验证支持该参数；不支持时，多信任域共享 Worker 要关闭 prefix caching 或按信任域隔离 Worker 池。官方当前说明了请求级 `cache_salt` 对缓存复用的隔离作用，但仍需针对锁定版本实测。[vLLM Prefix Caching](https://docs.vllm.ai/en/latest/design/prefix_caching/)

### R05 · P1 · token、模型身份和 API 兼容范围不明确

位置：原 §7、§9、§15–16、§18。

`model` 字符串不能区分模型 revision、tokenizer、chat template、上下文上限和渲染选项。对消息文本直接计数、去空白或“normalize token IDs”会让成本、长度校验和 prefix 语义偏离实际模型输入。长文本 tokenization 若直接在事件循环执行，也会拖慢所有流。

修正：增加 ModelSpec；对 chat 使用同版本模板和 tokenizer，fingerprint 基于实际 token IDs 的确定性序列化，包含模型/模板身份和 prefix 长度。默认只承诺文本 chat、单个字符串 completion、`n=1` 的明确子集；不支持字段返回明确 400，不静默忽略。限定请求体后再解析、鉴权后用有界执行器 tokenize；精确校验 `prompt + effective_max_output <= max_model_len`。官方确认 chat 依赖模板，模型仓库 generation config 也可能影响采样默认值，实验必须固定两者。[vLLM Server](https://docs.vllm.ai/en/latest/serving/online_serving/openai_compatible_server/)

### R06 · P1 · 取消和慢客户端仍是意图，没有可验证的资源回收路径

位置：原 §20.3–22，行 945–1014。

关闭客户端连接并不构成“GPU 已释放”的证明；不能假定存在通用 `/cancel` API。HTTP 连接池等待、下游写阻塞、无限 SSE 行和前导事件都可能消耗资源。

修正：明确上游 response 的所有权，所有退出路径进入 bounded cleanup；关闭上游连接并通过真实后端实验验证 abort。增加 pool timeout、downstream send timeout、cleanup timeout、SSE 单事件/预提交缓冲上限。HTTPX 的 read timeout 是数据块等待时间，不能替代业务首输出或整体 deadline。[HTTPX Async](https://www.python-httpx.org/async/)、[HTTPX Timeouts](https://www.python-httpx.org/advanced/timeouts/)

取消成功的 GPU 验收须在隔离 Worker 上观察 running/waiting 和后续 token 增长停止；缓存可能保留供复用，不能要求显存或 KV 使用率立刻归零。对后端取消未确认的 attempt，保留有期限的保守负载标记并限制该 Worker 新流量。

### R07 · P1 · 排队、准入与降级状态缺少单一责任方

位置：原 §18–19、§28、§41。

`max_queue_depth` 没说明是 Gateway 队列还是 vLLM waiting；Semaphore 的无限等待也可能形成隐式队列。DEGRADED 的“低优先级”未定义，KV 高占用也不单独证明过载。

修正：首版 Gateway 等待队列为 0，容量不足立即拒绝；vLLM waiting 是独立软阈值。入站解析/tokenization 同样限并发。429 表示租户/RPM 超限，503 表示全局/模型池无容量，413 表示字节超限。降级采用持续窗口和恢复滞回，不引入未定义优先级；先实现静态容量门槛，后以压测验证动态降级。

### R08 · P1 · metrics 新鲜度、健康与重启代次混在一起

位置：原 §9–11、§24–26、§40 F3。

metrics 抓取失败不等于推理进程死亡；指标缺失不能填 0；histogram 不能直接生成单请求耗时；Worker 同 endpoint 重启后旧 affinity 和 EWMA 也不应继续使用。

修正：Registry 区分 membership、health、metrics freshness 和 instance epoch。Collector 使用版本化 adapter 和真实 `/metrics` fixture，处理多 label、counter reset、缺失/NaN。负载陈旧时先停用高级分数并降级 RR+本地容量门槛，超过硬 TTL 再摘除；全部不可用返回 503。非瞬时错误需要失败阈值和恢复阈值，避免抖动。指标名称及定义以锁定版本实际输出为准。[vLLM Metrics](https://docs.vllm.ai/en/latest/design/metrics/)

### R09 · P1 · Benchmark 可能混淆 chunk、token、队列与请求成功率

位置：原 §33、§35–39、§43–44。

Gateway 的首输出等待包含网络、后端排队、prefill 和前端处理，不能仅凭本地 span 拆出精确后端 queue/prefill。SSE chunk 可能包含多个 token；仅统计成功请求的延迟也可能让大量拒绝的策略显得更快。Open-loop 若等待并发槽才生成下一个到达事件，会悄悄退化成 closed-loop。

修正：保存计划到达、实际发送、首有效输出、末有效输出、结束、usage 和 outcome。chunk 间隔单独命名；没有可信 token 数时 TPOT 标记不可用。后端 queue/prefill 采用后端指标，只有验证过 trace 关联后才谈逐请求分解。官方也区分流式输出间隔与请求级 TPOT。[vLLM Metrics](https://docs.vllm.ai/en/latest/design/metrics/)

每轮固定完整到达轨迹，报告 offered/sent/admitted/completed/goodput 与失败/拒绝分母；生成器落后或达本地上限要显式记为无效/丢弃，不能隐性排队。做冷/热缓存分离、试验顺序随机化、重复运行和置信区间；调参集与最终评估集分离。原“RR 不能作为最终推荐策略”应改为由结果决定，允许零收益和负收益结论。

### R10 · P1 · Kubernetes 部署尚未定义如何直达目标 Replica

位置：原 §6、§10、§26、§45。

若 Scheduler 选定 Worker 后仍请求普通负载均衡 Service VIP，实际处理 Replica 可能与选择不同。仅描述 Worker SIGTERM，也没有解决 Gateway 如何得知 drain、删除事件延迟和遗失后端请求。

修正：采用 EndpointSlice/Pod 发现并直连 Pod endpoint，保留 Pod UID/容器实例身份；名单变化和 drain 在同一 Registry 门禁生效。EndpointSlice terminating 端点的 ready 为 false，但这不会自动更新应用内 Registry，需要实现 watch/relist。Gateway drain 与 Worker drain 分开验收，Pod grace period 覆盖通知、在途请求和清理时间。[Kubernetes Pod Lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/)

v1 强制一个 Gateway Pod、一个 ASGI worker，滚动发布建议采用 Recreate 并接受短暂不可用；默认 Deployment rolling overlap 也会暂时出现两份限流账本。多 Gateway 的全局限流不在 v1 承诺中。

### R11 · P1 · 阶段安排把可靠性和测量基础放得过晚

位置：原 §47，行 2034–2143。

先实现四种策略，再添加取消、预占、超时和指标，会迫使调度器和 proxy 返工，也无法判断前期性能数据是否可信。

修正顺序：协议/账本与 fake Worker → 可靠流式 Gateway → RR/Least Load → 真实后端契约 → Cost/Prefix → 完整实验与 Kubernetes。最小 benchmark 和基础 metrics 从第一个可运行版本开始；图表和高级 trace 可以后补。

### R12 · P2 · Prefix affinity 的收益和内存边界还不够可解释

位置：原 §16–17、§31、§36 W5/W6。

固定很短的 N 可能把大部分请求映射到共同 system prompt；TTL 只按时间失效，不能限制高基数请求下的表容量。“成功开始执行”和“失败不增加”对首输出后失败的请求有歧义。

修正：首版只在请求正常完成后写 affinity，每项按 worker epoch 保存最后成功时间；TTL+LRU+最大条目数，重启/不健康立即失效。N 是经过模板渲染后的 token 数，按 workload 配置并记录；请求短于 N 时不建该 fingerprint。affinity 分数有界，先执行容量硬门禁再评分。将 affinity 命中与引擎真实 cache hit 分开统计。

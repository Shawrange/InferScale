# P4 实验工具：原生 Linux 服务器运行

P3 已按秋招范围通过，取消采用人工确认；本阶段不重复追补 P3 取消证据。先运行一轮检查数据产物，再安排正式 GPU 实验。工具已实现，不等于性能结论已产生。

## 1. 更新 Gateway，保留原生服务器配置

解压新包到新目录，保留旧目录备查。把服务器正在使用的 `configs/server.yaml` 复制到新项目中，保留 127.0.0.1:8100/8101 地址和真实模型身份。新包不包含该私人配置，也不包含模型或虚拟环境。

```bash
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install uv==0.12.17
uv sync --locked
python -m pytest -q -p no:cacheprovider
python -m inferscale.benchmark plan --config configs/server.yaml --output runs/p4-plan
```

`plan` 保留原生后端地址，生成四份策略配置和随机排列的 36 项作业清单（3 负载 × 4 策略 × 3 轮）。它不操作进程。停止旧 Gateway，再从新目录启动，否则无法记录本轮新增的 attempt 终态与客户端关联 ID。

## 2. 生成固定轨迹和环境记录

```bash
mkdir -p runs/p4-traces
for workload in mixed shared_prefix hot_prefix; do
  python -m inferscale.benchmark generate --workload "$workload" --seed 42 --duration 60 --rate 2 --output "runs/p4-traces/$workload.json"
done
cp configs/p4-environment.example.json runs/p4-environment.json
```

环境模板来自你提交的 P3 配置，仍需核对每个字段，特别是实际生效的 generation config；不能保留 `REPLACE_WITH_ACTUAL_EFFECTIVE_VALUE`。工具同时记录源码摘要、客户端依赖和完整 Gateway 配置，环境 JSON 是人工填写的服务器信息。

60 秒、2 req/s 是起步参数，不声称能压满双 4090。先小规模试跑，根据拒绝率与负载情况确定正式负载档位，再固定轨迹。所有策略用同一文件，禁止看过策略结果后单独调负载。至少三轮之外，稳定 P95 往往还需延长窗口。

三个数据集：Mixed 混合长短输入与 32/256 输出上限；Shared Prefix 共享长文档、后缀不同；Hot Prefix 约 85% 热前缀和 15% 独立背景。**输出上限不是实际输出长度**，实际长度使用 backend usage。每轮固定一个 seed warmup，干净 Gateway 的第一个 Worker 接收该种子，因此缓存/亲和初始状态可对齐；这不是强制制造不对称在途负载。

## 3. 单轮冒烟

终端 A：

```bash
mkdir -p runs/p4-logs
set -o pipefail
python -m inferscale.main --config runs/p4-plan/round_robin.yaml --port 8000 2>&1 | tee runs/p4-logs/mixed-round_robin-r1.log
```

终端 B（激活同一 Gateway 环境）：

```bash
python -m inferscale.benchmark run --trace runs/p4-traces/mixed.json --config runs/p4-plan/round_robin.yaml --policy round_robin --mode closed_loop --capacity 4 --gateway-log runs/p4-logs/mixed-round_robin-r1.log --environment runs/p4-environment.json --output runs/p4-smoke
```

closed_loop 只做固定并发的有限轨迹冒烟，不是固定到达负载；报告自动排除其正式比较资格。成功后检查 requests/attempts 和 summary，尤其 `attempt_evidence.complete`。

## 4. 正式 open-loop 轮次

严格复现采用 fresh_seeded：每轮重启两个后端进程，使 prefix cache 干净；同时重启 Gateway 清空 EWMA/affinity/账本。按照相同启动参数和模型版本等待后端 ready，完成相同的引擎预热流程；不要用测量数据预热，再交给工具执行同一个 seed warmup。后端编译缓存可保留，但每轮流程必须一致。

若不重置缓存可先用默认 uncontrolled 做探索，工具仍保存数据，但不会把该轮纳入正式收益比较。`--cache-condition fresh_seeded` 是操作者对流程的声明，工具不会自动清理或证明服务器缓存已重置。

按 `runs/p4-plan/jobs.json` 顺序执行。每次终端 A 只运行一个 Gateway，配置路径、日志名及下面的 policy/round/output 要一致。例如：

```bash
# 终端 A，旧 Gateway 已退出、后端已完成同样的重置/预热
python -m inferscale.main --config runs/p4-plan/cost.yaml --port 8000 2>&1 | tee runs/p4-logs/mixed-cost-r1.log
```

```bash
# 终端 B
python -m inferscale.benchmark run --trace runs/p4-traces/mixed.json --config runs/p4-plan/cost.yaml --policy cost --round 1 --mode open_loop --capacity 32 --timeout 60 --drain 65 --lag-tolerance 0.05 --cache-condition fresh_seeded --gateway-log runs/p4-logs/mixed-cost-r1.log --environment runs/p4-environment.json --output runs/p4-results/mixed-cost-r1
```

原生配置和 `/health/live` 的策略必须与 `--policy` 相同，否则在发生成流量前失败。全局/per-worker 容量仍由 Gateway 统一控制。测量期间不要混入 smoke、手动请求或其他客户流量。正式轮次所有策略使用相同的 client capacity、超时、SLO 和到达轨迹。

工具先用后端 `/tokenize` 校验所有独特 prompt 的长度（不计测量时间），随后执行 warmup；测量起点在其后。独立渲染 RTT 仍包含在 Gateway 的客户端 E2E/TTFT 中，每个策略一致。

## 5. 产物与复算

每轮目录保留 `trace.json`、`manifest.json`、`requests.raw.jsonl`、关联后的 `requests.jsonl`、`attempts.jsonl`、Gateway 日志、后端 before/window-end/after-drain 三组 metrics、`summary.json`、`report.md`。测量中逐条落原始样本；中断时 manifest 标 incomplete，不能拿残缺数据生成完整报告。目录已存在时拒绝覆盖。

```bash
python -m inferscale.benchmark report runs/p4-results/mixed-cost-r1 --gateway-log runs/p4-logs/mixed-cost-r1.log
python -m inferscale.benchmark compare runs/p4-results/* --output runs/p4-comparison
tar -czf inferscale-p4-results.tar.gz runs/p4-results runs/p4-comparison runs/p4-plan runs/p4-traces runs/p4-environment.json
```

如日志尚未刷完导致 attempt 缺失，等 Gateway 静止后再 report；缺失不会被伪造为 0 次。策略、版本、配置、轨迹或缓存条件不同会分入不同 comparison_group；每组每策略至少三轮有效结果，报告保存均值、范围与逐轮终态分母。先别凭一次 P95 下结论。

## 统计边界

- open-loop 使用绝对计划时间；客户端槽满立即 not_sent，不等槽位再声称维持原到达率。发生丢发或发送延迟超过阈值时标记发送器受限。
- 只有收到有效 finish + DONE 才成功；role/usage 不算首内容。空文本 TTFT=null，usage 缺失时 token 吞吐/TPOT 不伪造。
- 吞吐只计窗口内成功终结；drain 后成功单列。timeout 是 failed 的子类，不重复计数。chunk interval 不叫 token ITL，TPOT 只是有可信 usage 时的估计。
- 首末稳定缓存快照用于 before→after-drain 的 cohort 增量，不冒充精确窗口命中率。快照顺序采集；缺系列、counter 回退或 created 变化时不算有效增量。缓存单位需与后端 HELP 核对。
- Gateway 日志的 client_request_id 仅用于关联；原始逻辑 request_id 与每个 attempt_id 独立。服务器时钟不与客户端时钟直接相减。
- 当前提供请求级原始数据、Markdown/JSON/CSV 汇总；正式图表、策略收益解释，以及 direct 单 Worker 对照在拿到真实结果后继续完成。无数据时不生成收益图。
